# 03 — Product landscape

Research date: 2026-09-10. Nine named products are covered, including Crystal as a discontinued predecessor. Sources below were opened, not merely found in search. Capabilities are vendor or maintainer claims; no product was installed, benchmarked, or independently security-audited. Download counts, testimonials, and performance slogans are not evidence of quality or demand. License names describe only the explicitly identified component; omission means unverified.

## What converges, and what remains different

Inference from the matrix: task → isolated checkout → agent run → review → integration is the common workflow. UI forms differ—terminal trees, kanban, IDE, or visual editors—but merely placing several CLIs beside a Git diff no longer creates a distinct product.

Important differences are execution ownership (local processes, owned remote host, vendor cloud), the recovery contract (reattach to a live process versus resume a conversation versus restore a layout), and the evidence attached to review. Worktree separation should never be presented as an OS security sandbox. Model subscriptions also remain distinct from the workspace's own state and permissions.

The closest implementation-scope comparison is Emdash; Superset is another substantial overlap. cmux is particularly relevant to persistence and programmable terminal control. Cloud products compete on unattended execution and team coordination. Nimbalyst competes on visual work artifacts. These are product-position observations, not measured rankings.

## Three differentiation hypotheses

1. **Reliable Linux/WSL continuity.** A focused workspace could earn preference if it preserves agent and ordinary development processes through GUI failure, reports WSL shutdown honestly, and reconstructs task context without replaying commands. Persistence alone is insufficient; measurable recovery and comprehensible state are the hypothesis.
2. **An evidence-centered review queue.** Developers may value one place showing each task's accepted scope, base revision, changed files, required checks, unresolved decisions, and handoff notes. The hypothesis is lower human review effort and fewer missed failures, not greater agent throughput.
3. **Portable configuration with visible changes.** Users may prefer project-owned recipes and context manifests that show which agent receives which hooks, MCP entries, instructions, and secret references, with selective application and rollback. Cross-provider configuration itself already exists; predictable behavior and low migration cost need validation.

None establishes market demand, exclusivity, or willingness to pay.

## Three reasons not to build a generic agent-terminal wrapper

1. **Feature overlap is extensive.** Worktrees, provider choice, notifications, remote access, and saved context are already available in several forms. Recreating them creates continuing compatibility work without demonstrating a switching benefit.
2. **Visible usage can coexist with weak economics.** Bloop attributed its shutdown to predominantly free usage and failure to find an attractive business model. This is one company's report, not proof that the whole category cannot work. [Shutdown announcement](https://vibekanban.com/blog/shutdown).
3. **Provider and environment churn can consume the roadmap.** Different hook semantics, configuration formats, credentials, resume mechanisms, and local/cloud boundaries require ongoing maintenance. A product promising every integration immediately risks making reliability worse than the user's existing terminal workflow.

## Validation before expanding the release

These are proposed experiments, not results or already approved development work.

| Experiment | Comparison and decision evidence |
| --- | --- |
| Recovery drill | On Linux and WSL, run the same agent task, test watcher, and server in plain tmux, MINIMAL, and available Emdash/cmux setups. Interrupt GUI, attachment, network, and host separately. Record duplicate launches, lost state, recovery time, and whether status matches reality. Require zero unintended command replay or silent task loss in the tested scenarios. |
| Review study | Recruit 6–8 developers already using parallel agents; counterbalance the same seeded changes between their current workflow and a MINIMAL prototype. Measure time to find failed checks, scope drift, and conflicting changes. Proceed only if review improves without increasing missed defects; set the numeric threshold before running the study. |
| Portability and retention trial | Have users import an existing project, inspect a proposed hook/MCP change, switch agent, export, and remove MINIMAL. Measure configuration damage, setup effort, and whether they voluntarily reuse it over two weeks. Interview non-returners. Discuss price only after observed repeated value; stated interest alone is insufficient. |

## Lean release recommendation

Design a local Linux/WSL release around a single complete loop: create a scoped task, choose installed Codex or Claude Code, allocate/import a worktree, attach a persistent terminal, inspect evidence, and explicitly complete or archive the task. Retain ordinary shell terminals so the surrounding development environment remains usable.

Specify durable task/run identity, clear running/waiting/exited/unknown distinctions, a small review checklist, conservative cleanup, context export, and project recipes whose proposed configuration changes are previewable. Existing state must remain usable through GUI restarts; host reboot must show interrupted work, not imply continued execution.

Keep remote runners as a later extension point. Defer a hosted service, team permissions, workflow graph designer, automatic merges, broad plugin marketplace, native mobile clients, and a full IDE until the experiments identify a repeated need. The next product decision should follow observed recovery or review improvement, rather than the number of integrations in this matrix.
