# 08 - Git ownership, review evidence, and DevOps

Accessed: 2026-09-10. Scope: architecture research for MINIMAL's Linux/WSL Electron and TypeScript workspace, persistent tmux terminals, scoped file helper, and future installed-agent orchestration. No repository workflow, infrastructure, account, or application was changed. Recommendations below are proposed contracts, not implemented guarantees.

## Official observations

These nine fetched official pages describe supported semantics. Each source summary is under 110 words; no quotations are reproduced.

| Technology / source | Observed behavior |
| --- | --- |
| [Git worktrees](https://git-scm.com/docs/git-worktree) | Linked worktrees have separate working files, indexes, and HEADs, while sharing most repository infrastructure, branch refs, and default repository configuration. Adding a worktree checks out a chosen commit; it does not transfer another checkout's uncommitted files. A worktree lock protects against pruning, moving, and deletion; it is not an edit lock. Git normally refuses a branch already checked out elsewhere, with force overrides available. |
| [Git repository layout](https://git-scm.com/docs/gitrepository-layout) | The default hooks directory resolves through the common Git directory for linked worktrees. Hooks are executable customization scripts used by Git commands. A separate checkout therefore does not imply independent hook ownership or an independent trust boundary. |
| [Git revision parsing](https://git-scm.com/docs/git-rev-parse) | Git can resolve repository paths and verify object identities. Type suffixes distinguish a commit from its tree; `--end-of-options` protects untrusted revision arguments from option interpretation. The object format is discoverable, so applications should not assume every object ID has forty characters. |
| [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use) | GitHub recommends minimal token permissions and full commit SHA pinning for actions. Privileged `pull_request_target` and `workflow_run` jobs must not check out untrusted PR code. Artifacts from other workflows also require scrutiny. Persistent self-hosted runners can be compromised by untrusted jobs; environment approvals do not isolate that machine. |
| [Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) | A concurrency group admits one running job or workflow. The default pending slot replaces older pending work. Current documentation also offers `queue: max`, allowing up to 100 pending entries; it cannot combine with `cancel-in-progress: true`. Groups are case insensitive. Queue order follows when work starts waiting, so dispatch order is not guaranteed. |
| [Actions scheduled events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) | Schedules use the default branch and can be delayed or dropped under load. Public repositories lose active schedules after sixty days without repository activity. The minimum interval is five minutes. UTC is the default; current documentation supports an optional IANA time zone. Consequently, scheduling is not a guaranteed delivery or exact-time service. |
| [Actions environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) | Protection rules gate jobs referencing an environment. One listed reviewer can release a job; self-review prevention and administrator-bypass controls are configurable. Environment secrets become available after required approval. Branch restrictions use the workflow's ref. Required-reviewer availability depends on repository visibility and account plan. An environment gate does not itself inspect an artifact digest. |
| [Actions OpenID Connect](https://docs.github.com/en/actions/concepts/security/openid-connect) | A workflow can exchange a GitHub OIDC identity token for short-lived cloud credentials. The cloud provider validates configured identity claims against its trust policy. This removes the need to duplicate long-lived cloud credentials into GitHub, but the trust policy and granted cloud permissions still determine authority. |
| [Terraform apply](https://developer.hashicorp.com/terraform/cli/commands/apply) | Applying a saved plan executes its recorded decisions without interactive confirmation; supplying the plan is treated as approval. Applying without one creates a fresh plan. State locking should remain enabled. A failed apply can leave partial infrastructure changes, and Terraform does not automatically roll them back. |

## Recommended minimal integration ladder

1. **Observe the existing workspace.** Keep ordinary terminals usable. Display the actual checkout, branch, base commit, and dirty state. Import must not silently stash, reset, commit, run setup, or initialize Git. Non-Git directories begin with one managed writer and explicit snapshots. GitHub Actions and Terraform are optional later integrations, not prerequisites for opening a terminal.

2. **Own managed writes.** Store a checkout lease with run ID, generation, and acquisition state; include editor saves and the file helper in the same admission policy. On restart, reconcile the previous process before assigning another writer. Lease expiry alone cannot stop an old shell. Same-user processes can bypass application checks through direct filesystem access: OS users, mount permissions, or another verified isolation boundary must enforce stronger claims. A worktree lease and `git worktree lock` serve different purposes.

3. **Prepare parallel work explicitly.** Allocate a unique branch/worktree from a pinned committed base. When a task needs existing dirty changes, present a manifest of selected tracked edits and untracked inputs, then create an authorized snapshot without modifying the source checkout. Record excluded ignored files and secrets. Serialize application-managed mutations to shared refs, configuration, and worktree membership through a repository-level coordinator. Inspect effective hooks before Git mutation. Give tasks separate ports, generated data, and test services where necessary.

4. **Verify one combined candidate.** Integrate task outputs into a candidate workspace. Record repository identity, intended target, base commit B, candidate commit C, tree T, diff digest, recipe/tool/environment versions, and verification artifacts. Resolve C and T with Git's verified commit/tree syntax. Run checks against a fresh candidate checkout with no other managed writer. Hash any non-Git inputs needed by those checks. Check for changes before and after verification; this detects managed mistakes but cannot prove integrity against hostile same-user writers. The evidence view must distinguish passed, failed, skipped, and unavailable checks.

5. **Promote under scoped authority.** Before updating the target, reacquire ownership and require the target still to equal B, and the candidate/evidence still to match C and T. A base change requires a new candidate and applicable verification. Use an atomic expected-old-value operation where the destination supports it; an earlier hash check alone leaves a race. Keep result acceptance, remote publication, merge, and deployment as separate recorded operations. Existing valid grants can authorize them; task completion must never implicitly grant merge or deployment authority.

For CI, initially produce build/test reports bound to the candidate commit and workflow revision. Keep untrusted PR execution in disposable restricted runners with read-only repository access. A privileged promotion job must validate the exact producer run, revision, artifact identity, and digest it consumes. A green job name or model-written summary is insufficient evidence.

For deployment, expose the target environment, artifact digest, workflow revision, and concrete operation before approval. Recheck that tuple inside the gated job; changing it invalidates the approval. Use a distinct deployment concurrency group and avoid automatic cancellation of an active apply. Check provider-specific OIDC audience/subject conditions and grant only the required environment authority after the gate.

For Terraform, propose a two-step saved-plan workflow: produce and inspect the plan, then bind authorization to its digest, configuration revision, backend/workspace, environment, and tool/provider versions. Protect plan artifacts as sensitive. The apply job must consume that exact plan; it must not quietly regenerate one after approval. Missing or stale evidence returns to review. OpenTofu is a candidate adapter, but compatibility and its version-specific behavior require separate validation.

Cancellation requests stop work; they do not undo pushes, cloud operations, or files already written. After interruption, report unknown or partial effects, reconcile external state, and require a deliberate recovery operation. Do not assume killing a process immediately revokes issued credentials. Scheduled CI is suitable for best-effort maintenance reports; critical routines need persisted occurrence accounting, missed-run visibility, and an available execution host.

## Five acceptance tests

1. **Dirty import:** With staged, unstaged, untracked, and ignored files present, import changes none of them. A new task sees only its selected base and explicitly included snapshot inputs; the receipt lists exclusions.
2. **Ownership recovery:** Two managed writers requesting one checkout cannot both start. Restarting the runtime while the old writer survives does not transfer ownership blindly. A normal worktree lock does not pass a sandbox test; enforceable isolation must independently block forbidden writes.
3. **Candidate freshness:** After successful checks, move the target base, edit the candidate, or replace an evidence artifact. Each mutation blocks promotion until the required candidate/evidence review is renewed. Two separately passing branches cannot substitute for checks on their combined result.
4. **Approval and CI provenance:** Substitute an artifact or saved plan after environment approval, or submit a PR that attempts privileged code execution. Promotion rejects the mismatch; untrusted jobs receive no deployment credentials. A matching previously granted operation proceeds without redundant confirmation.
5. **Interruption and missed work:** Interrupt a fake deployment after one externally recorded effect and inject a missed scheduled occurrence. The UI reports the partial effect and missed occurrence, performs no automatic replay, and records any explicitly authorized recovery separately.

## Unknowns and corrections to carry forward

The draft architecture already correctly separates worktrees from sandboxes and verification from acceptance. Make shared hook ownership, repository-level coordination, dirty-input receipts, and artifact-bound deployment authority explicit.

Still unverified: the real application's Git integration; minimum Git/runner versions; submodule and large-file behavior; provider CLI restrictions on direct Git commands; the user's GitHub plan and rules; cloud trust policy; Terraform backend locking and drift policy; secret-safe artifact retention. This research executed no acceptance tests. Do not advertise scheduled delivery guarantees, automatic rollback, enforced leases, or OpenTofu parity before those contracts are tested.
